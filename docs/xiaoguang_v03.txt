一条贯穿全文的体验线索
贯穿体验改用你提出过的真实讨论场景：用户先想了解“显化是什么、小光能做什么”，随后把健身愿望变成可执行计划；连续三天没有锻炼时，小光不擅自贴上“三分钟热度”的人格标签，而是根据他在“重新认识我”中选择的互动方式回应。用户可能从不写日记，但通过聊天积累好消息；14/30 天后，小光用真实生活片段做出一份惊喜的蜕变报告。


01  创意方向｜能做什么
设计原则：小光是一位随着相处变得越来越了解用户的行动伙伴，显化是“更清楚地想要什么、感受到可能性，并推动实际行动”的体验语言，不承诺靠想象就能改变客观现实。
1.1 产品愿景
一句话定位｜显化概念包装的长期个人成长 Agent：同一个小光理解用户的目标和状态，能用产品工具协助行动、主动关怀、保存生活细节，逐渐更懂用户；不是原封不动接入聊天模型。
【你提出的场景】初次见面用户可能先问“小光，你会什么？显化是怎么回事？”小光能说明自己的能力，带着用户认识自己，再自然地设定计划；往后同一个 Agent 逐步承担提醒、陪伴和建议的角色。
相对于聊天机器人｜不仅“回答得好”，更要“知道用户正在做什么、必要时执行应用内操作、几天后能接上前文”。模型负责理解与表达，产品负责状态、记录和推进。
【你提出的场景】参考 Muse 的日常陪伴：用户不必每次都主动敲开聊天，小光可以结合已有计划和近况，在合适的时候发出新的聊天消息；首版只在 Web 聊天窗口内呈现，不宣称已实现手机系统推送。
相对于待办/日记 App｜用户无需自己维护一套复杂系统：聊天就能生成可执行计划、记录好消息、回顾成长；同时提供可视化页面，方便查阅和管理。
【你提出的场景】用户平常没有写日记的习惯，小光可以在聊天时捕捉值得保存的“好消息”，获得确认后帮他留下记录；用户不必为了记录生活每天专门打开一张表单。
产品真正的高光时刻｜不靠密集通知与虚假鼓励，而靠准确的小细节、恰到好处的帮助，以及 14/30 天后能触动人的蜕变报告。
【你提出的场景】相处到 14 天或 30 天，小光能把过去那些看似普通的小事串成蜕变报告，让用户惊讶于“原来你都记得”。不能为了感动人而虚构事件或夸大变化。
能力边界｜可做目标拆解、习惯支持、情绪整理、一般生活建议、产品内记录与检索；不可自称专业治疗师、包办现实世界行动、凭空创造用户经历，或提供产品目前没有接入的能力。
【边界验收补充】用户要求小光调用并未接入的外部服务时，它应说明暂不支持；当前定位不包含 Muse 的云电脑、复杂研究执行或跨应用自动操作。
待确认  愿景关键词可保留“显化”，但对外介绍是否突出“把愿望变成行动”作为主要利益点，需要一次明确的产品定位决策。
1.2 目标用户
优先探索的人群｜有具体愿望却容易中断行动、希望被正向陪伴的人。需求可能从显化开始，实际包含运动、生活习惯、目标拆解、心态整理与个人成长。现阶段这是产品假设，需用户研究验证。
【你提出的场景】用户想开始健身，却有连续三天没有完成的情况：小光应了解原因并结合用户偏好决定怎么跟进，而不是马上认定他是“三分钟热度”。
第二类｜没有主动写日记习惯、但希望生活被看见的人。价值不是强制每天打卡，而是 Agent 在合适时机协助保留好消息与回忆。
【你提出的场景】有些人其实经历了不少值得开心的事情，却不会写日记。经过一个月，报告突然把这些被忘记的小事重现出来，形成“有人帮我记住了生活”的体验。
第三类｜喜欢养成、成就和生物进化路径的人。个人宠物从基础形态逐渐成长为幻想生物，是与 Agent 陪伴并行的游戏化奖励，不代表 Agent 外观必须同步变化。
【你提出的场景】个人宠物的成长可探索“细胞→蝌蚪→乌龟→更奇幻的山海经风格生物”等阶段或分支；这是一条宠物成长路线，不是说小光的聊天形象每天都要换。
非优先人群与风险边界｜需要专业心理危机干预、医疗诊断、投资等高风险建议的人，不应被引导将小光视为替代专业人士；强工具/代码代理需求也不作为当前核心定位。
【安全验收补充】出现高风险心理或医疗诉求时，小光不能假装具备专业资质；产品把支持与适当转介放在积分反馈之前。
首次进入的分层体验｜愿望清晰的人直接开计划；不知道做什么的人从点子场景探索；偏内向或不想填问卷的人允许跳过，再逐步了解。
【你提出的场景】用户刚进入产品，可以先了解显化、小光以及成长系统；也可以直接问“我什么时候可以进化到下一阶段？”，小光应知道真实的解锁规则，而不是编一个答案。
待确认  用访谈或小规模种子用户验证：最能引发留存的价值究竟是行动陪伴、生活回顾，还是成长形象；不要只凭内部偏好决定首页权重。
1.3 核心功能
功能以八个可理解的模块组织，但“小光 Agent”贯穿所有模块、可主动调用产品内工具；主动触达是横向机制，不单设一个孤立页面。

A. 小光 Agent｜所有能力汇合点
连续的同一个伙伴｜引导时可以教用户怎么玩，日常可以陪练和提醒，低落时可以倾听；不是不断切换多个“专家人格”。
【你提出的场景】用户问“下一级要多久才能解锁？还有什么内容？”同一个小光能查询应用规则作答；用户接着说生活里的烦恼，它继续陪伴，不切换成另一个专家机器人。
带工具的对话｜小光明确区分“聊聊这个话题”和“已经帮你记下来/完成步骤”。涉及写入、修改、公开分享时给出可核对的结果。
【基于你的计划场景扩展】用户明确要求调整健身安排时，小光调用工具修改实际步骤，成功才说“已修改”，否则说明未写入。
B. 蜕变计划｜想法落成能做到的小事
目标拆解｜先澄清用户想要的结果、时间与现实约束，再生成轻量的周计划；初期允许一条主要计划与少量步骤，避免复杂项目管理。
【你提出的场景】用户希望小光协助制定健身或习惯计划。小光不是直接塞一张完美日程表，而是先了解当下状态、目标和能做到的频率，再写入可执行步骤。
温柔复盘｜中断不直接判定用户不自律；鼓励缩小目标、变更时间或暂停，并保留事实。
【你提出的场景】三天没锻炼只是带日期的事实，不是人格结论。小光在“重新认识我”中已问过用户此时更喜欢被催促、一起分析原因还是暂时不提，后续按选择互动。
C. 好消息｜日常正向记录
低门槛记录｜一件完成的小事、值得开心的瞬间、勇敢迈出的一步，都可以由用户讲述后被保存；记录“发生了什么”而非只打“开心”标签。
【你提出的场景】用户没有写日记的习惯；聊天中讲到生活里的好事，小光适当询问要不要记录，逐渐留下日后能回看的个人生活故事。
分享与隐私｜默认私密；记录不等于自动发布。分享卡需要明确预览，敏感姓名、地点等默认不外露。
【隐私验收补充】用户决定把一条私密好消息做成分享卡时，先看到预览，并自己决定要公开哪些细节；私人记录绝不因为生成报告而自动公开。
D. 成长进化｜游戏化但不鼓励刷分
经验值规则由业务端控制。你提出的讨论示意：每日总经验 120 XP；行动、好消息、显化练习、签到等来源可各设 30 XP 上限；这是讨论数字，不是已经锁死的最终配置。
【你提出的场景】如果每类上限暂定 30、每日总上限 120，那么用户将同一件事拆成许多条记录也不应无限拿分；后端要按真实行为、来源和日期去重。
个人宠物进化｜独立于小光 Agent 的聊天形象。宠物可从细胞、蝌蚪、乌龟等形态发展到带有山海经灵感的幻想生物，并探索分支路径。初版用统一的人工制作素材，不依赖实时生图。
【你提出的场景】成长页中，用户看到自己的宠物从细胞成长到类似蝌蚪、乌龟的形态，再逐步探索更奇幻的分支；聊天页的小光仍可保持 Grok Bot 式稳定形象。
E. 我的空间｜个人资产和可控记忆
个人画像｜保存用户主动确认的重要偏好、当前目标、可展示的成长历程；让用户能查看、更正或删除，不偷偷推断成不可修改人格。
【你提出的场景】用户明确对小光说“帮我记住我喜欢吃寿司”，这条长期偏好应立刻写入、可查看修改，不应隔一阵子被系统无端遗忘。
时间线｜将已确认的好消息、关键目标调整、重要蜕变时刻合为私人生活时间线；与商业社交动态区别开。
【你提出的场景】即使用户平时不写日记，“我的空间”也能把小光帮他记下的好消息与阶段性改变组织成私人生活时间线。
F. 蜕变报告｜将真实记录变成有温度的故事
双周期｜14 天提供轻量惊喜回顾，30 天呈现完整成长旅程；数据不足时诚实承认，不编造转变。
【你提出的场景】在相处 14 天或 30 天后，小光回顾用户真实经历过的开心事和行动变化，做成有惊喜感的蜕变报告；不能像流水账，也不能凭空补写故事。
模板与真实性｜优先由设计师提供精致报告卡模板，Agent 负责从核实记录中选择叙事和填充文字；生成前再核对来源。
【你提出的场景】蜕变报告使用设计师做好的精致卡片模板库，AI 负责选取经过核实的故事与文字填充；普通社交分享卡可以更灵活。
G. 点子｜“原来还可以这样玩小光”
场景化能力展示｜独立主题库按生活、健康、愿望、与小光培养默契等分类。每张卡有一个明确可体验的触发话术和预期效果。
【你提出的场景】点开“重新认识我”，小光用约 10 分钟的具体情景提问：连续三天没健身时，你更希望它催促、一起找原因，还是先不提？用回答调整互动偏好。
可重复探索｜定期出现新的引导方式；不是纯静态图文展示，也不能触发未经授权的跨平台操作。
【你提出的场景】点子“现在小光有多了解我”让 Agent 说出它记得的内容，并承认还不确定的部分；用户可借此纠正画像，让小光逐渐变得更了解自己。
H. 心灵学堂｜可信内容，不是 AI 无限生成文章
人工维护的心灵学堂｜团队策划、审核并更新心理常识和显化相关知识，Agent 有阅读、解释与导流权限，但绝不直接创建、上传或修改官方文章。
【你提出的场景】学堂可以整理“水桶效应”等心理或认知相关概念，由团队审核内容；用户不理解时再让小光解释，并联系日常生活讨论。
Agent 只读并导流｜小光可以检索、概述、解释、推荐相应知识，但不能在对话中擅自更改、上传或发布学堂正式内容。
【你提出的场景】用户问“水桶效应是什么意思？”小光从团队维护的心灵学堂读取资料，用通俗话解释，必要时引导阅读原文；不会反过来把自己的回答自动写成学堂文章。
待确认  MVP 建议优先跑通“聊天→计划/好消息→可追踪记录→主动回访→回顾报告”闭环。八模块可以有入口，但不应同时做成八个重型系统。


02  技术方向｜怎么落地
技术目标不是堆最先进的名词，而是以可测量的可靠性、清晰的权限边界和合理的成本，让用户体验中的承诺真正可实现。
2.1 Agent 架构
架构决策｜采用“一个主 Agent + 按需 Skills / 工具 + 确定性业务流程”；当前不引入多 Agent 编排。主 Agent 理解意图、调工具、组织回复；后端对积分、权限、状态和报告事实负责。
【基于你的 XP 规则扩展】用户说“今天完成健身步骤了”，同一个主 Agent 找到对应任务并调用完成工具；后端依据每日 120 XP、来源各 30 XP 的讨论规则进行限额和去重，不让模型临时编分。
Skills 的角色｜Skills 代表渐进加载的场景说明、话术步骤与可用工具约束，不必对应独立模型；用户点“重新认识我”时加载该情景引导，结束后回归日常对话。
【你提出的场景】从点子“重新认识我”进入情境问答，系统只是按需提供引导 Skills 和可调用工具；依旧是原来那个小光，不必启动第二个专家 Agent。
后台确定性工作流｜明确的计分、进化解锁、定时任务、报告触发由代码和数据库完成，不让 LLM 自由“决定”经验值或篡改记录。
【你提出的场景】用户为了经验值把一个行动拆成很多小步骤，后端按计分来源和限额计算，不会因为小光“想鼓励”就多发经验。
编排层必要能力｜用户隔离、会话历史截断与摘要、工具白名单、参数校验、超时/重试、幂等请求、结构化日志、错误回退。
【方案验收补充】  完成步骤工具网络超时后重试，凭操作 ID 不重复完成与重复加分。
建议数据流：用户消息 → 意图理解/检索上下文 → 主 Agent 决策 → 授权工具 → 后端数据库与规则 → 结果回传 → 小光回复；后台另有日终记忆整理、主动回访、报告生成任务。
2.2 模型选择
按任务选模型，不按“参数越大越好”｜主对话优先考察中文理解、工具调用正确率、语气稳定性、延迟和成本；记忆摘要、卡片文案可按质量需求使用同一模型或更轻量模型。
【基于你原始场景设计的评测】把“帮我记住我喜欢吃寿司”“我三天没健身”“怎么解锁下一级”等对话交给候选模型，检查明确记忆、人格误判、规则检索和工具调用是否正确。
必测工具能力｜支持稳定的函数调用/结构化输出；能正确选择“不调用工具”；能根据后端工具失败原因给用户诚实反馈。
【基于你原始场景设计的评测】“我三天没健身”应进入事件判断和陪伴逻辑，不应自动写成“缺乏毅力”；“帮我记住我喜欢寿司”则属于明确存储请求。
上下文与成本｜对话窗口放入“必要的核心档案 + 当前业务状态 + 相关少量记忆”，而非将所有历史塞进提示词；跟踪每会话 tokens、工具轮数及 P95 延迟。
【你提出的场景】记忆系统只需要随用随取稳定的偏好、现行计划及必要的历史：例如“喜欢寿司”是核心长期偏好，不必每次为确认这点都回放整段对话。
降级策略｜优先保证记录不丢、工具结果真实。当模型响应慢或服务不可用时，提供可理解的提示；可用的非 AI 页面继续工作。
【Web 优先的降级场景】即使模型服务暂时不可用，用户仍可在网页版蜕变计划中手动操作；此项为技术验收补充，而非你最初举出的例子。
待确认  模型品牌/版本暂不写死。基于真实候选服务的工具正确率、端到端时延、成本和稳定性做一次小规模盲测，再锁定生产配置。
2.3 长期记忆
四类信息分开存｜①简短核心画像；②用户明确要求“记住”的受保护长期事实；③带时间/来源的事件记忆；④计划、经验值、进化等权威业务数据。心灵学堂与产品手册属于独立只读知识库。
【你提出的场景】“帮我记住我喜欢寿司”是明确长期记忆；“三天没健身”是近期事件，不能升格为“三分钟热度”的性格标签；经验值/进化状态是独立业务数据。
明确记忆即时写入｜用户明确指示“记住……”的内容应立即写入并可反馈/更正；除非用户删除或修改，不仅因时间推移就自动遗忘。
【你提出的场景】当用户说“帮我记住我喜欢吃寿司”，小光应立即写入可更正的显式记忆；哪怕很久没有提起，也不能仅因为经过一个月就自动删除。
隐性记忆按日整理｜普通聊天不必每轮触发昂贵记忆写入；每天异步汇总当日重要事件与行为，按新增/更正/去重增量更新；不每日重写整份画像。
【你提出的场景】日终异步整理当天真正发生的交流与行动，只更新有变化的档案部分，而不是每条聊天写一次记忆、每天又把整个用户画像重写一遍。
保守推断与证据强度｜不因一次表现贴人格标签；同类情境反复出现且对服务有用时，记录为可质疑的倾向而非身份结论。
【你提出的场景】用户三天没健身，最多记录为“连续三天未完成健身”；不能就此推断他“三分钟热度”。小光通过长期观察和用户明确反馈逐步了解偏好。
检索策略｜优先查询业务表中的准确数据；个人回忆用关键词/时间过滤 + 语义检索（可逐步升级为混合检索和重排）；不要求第一版就上复杂图数据库。
【你提出的场景】用户问“小光，你对我了解多少？”系统应取出有明确来源的记忆及业务状态；重要偏好常驻，过往事件按需检索，不靠模糊的单一人格标签。
用户掌控与纠错｜“我的空间”提供记忆查看、编辑与删除入口；重大偏好改变应可确认/撤销；敏感信息控制更严格。
【基于寿司案例扩展】若用户随后明确说“我现在不喜欢寿司了”，记忆系统应更新原有偏好，并保留可供纠错的变更依据，而不是新旧偏好同时无差别生效。
长文与隐私｜对超大上传内容采取摘要/分块/限额处理，不能因上传小说或资料就将书中描述当成用户自身经历；不同用户数据库必须完全隔离。
【你提出的场景】用户可能上传上百万字的文档；系统不能为“日终个人记忆总结”扫描并吞掉整篇材料，更不能把文档中的角色信息误认为用户个人经历。
待确认  先上线“明确记忆即时生效 + 事件带来源 + 每日增量整理 + 查看纠错”；验证检索质量后，再决定是否需要向量服务或知识图谱。
2.4 工具调用
工具注册表｜每个工具定义用途、参数结构、身份权限、是否写入、是否要求确认、幂等方式和错误信息；Agent 只能调用白名单。
【基于你的产品场景拆解】显式记忆写入、健身计划步骤、好消息记录、成长规则查询分别是不同工具；小光能决定何时调用，但无法绕过鉴权或经验值规则。
关键工具能力｜先覆盖“查记忆 / 写明确记忆 / 建立或修改步骤 / 完成步骤 / 保存好消息 / 开始场景 / 查询成长状态与规则 / 查询学堂内容 / 查询报告”。现有原型工具应逐一对照补齐。
【基于你的健身场景扩展】用户说“我完成健身了”，如果当天有多个步骤，Agent 应根据业务状态匹配或澄清，避免误勾选与重复积分。
读写与权限边界｜只读查询可自动使用；写入个人记录可根据用户意图明确性判断是否确认；删除、外发分享、敏感变更必须有更强确认。官方学堂仅有查询工具，无编辑发布工具。
【你提出的场景】用户直接说“帮我记住我喜欢吃寿司”，可即时写入；普通聊天里提到喜好或好消息，要结合语境谨慎判断，不把所有提及都擅自升级为永久记忆。
状态回执和回滚｜对话里的“已完成”必须有后端成功回执；失败要说明未写入。可更正错误步骤，避免“模型说记了，但数据没变”。
【后端验收补充】当保存记忆或好消息失败时，聊天窗口不得显示“已经记住”，也不能凭空增加 XP；这是产品承诺的技术保障。

2.5 技术评估
已有原型基础｜待实际核验｜交接材料描述：现有 Web 原型、Python + SQLite + 原生 JS、按用户隔离存储、主 Agent 及部分工具、FTS5 记忆检索、定时互动与初步报告机制。此为历史交接信息，不代表全部已通过生产验收。
【测试场景补充】在已有 Web 原型中分别登录两个测试用户，验证 A 的私人好消息和寿司偏好不会被 B 的搜索与报告读取。
关键问题清单｜真实记忆命中率/误记率未充分验证、模型服务延迟偏高、Embeddings 接口可能不可用、失败恢复和极端输入安全需核实。不要把模拟测试数量等同于真实可用。
【基于你原始场景设计的测评】隔几天再问“你记得我喜欢吃什么吗？”；再测试“一次三天没健身是否被错误标注性格”，用这些案例验证召回和误推断率。
质量指标与验收｜评估工具选择正确率、实际写入成功率、记忆检索精确率、跨用户数据隔离、错误标签率、首次响应与 P95 耗时、单日推理成本、主动触达退订率。
【你提出的场景】当用户陈述“三天没健身”，只说明近况而非明确要求修改计划，小光不应擅自调整步骤或增加任何虚构完成记录。
场景测试优先于模糊跑分｜设计跨天端到端脚本并重复执行；保留输入、工具轨迹、DB 前后状态和最终回复，便于快速回归。
【跨日验收补充】先说“帮我记住喜欢寿司”，过数日再问同一事实，应能稳定回答；用户正式更正后也要以新信息为准。
安全与合规评估｜限流、敏感内容处理、用户数据导出/删除、分享前确认、未成年人/心理脆弱场景的保护；产品表达不得声称科学证明“想象就能实现一切”。
【隐私验收补充】私密好消息和 30 天蜕变报告默认仅本人可见；分享到外部前需要独立预览和确认。
2.6 产品落地
实施顺序｜明确以现有服务器网页版为第一交付平台，产品和 UI 以桌面 Web 使用为第一设计目标；技术上做好响应式及模块解耦以便之后迁移移动端。第一版不实施原生 App、手机系统通知或必须对接的生图模型。
【你提出的场景】小光主动关怀在第一版体现为网站内聊天窗口的新消息；用户下次打开网页版可以看到。等网页版打磨好，才结合现有页面和交互迁移到移动端 App，并单独规划系统通知。
P0：跑通核心闭环｜主 Agent 稳定对话、两类可写工具（计划/好消息）、准确状态查询、明确记忆即时写入、简单成长计分、基本隐私规则、最小可用首页。
【你提出的完整体验】首次进入，小光解释显化及自身能力 → 用户提出健身计划 → 几天未运动时按约定方式陪伴 → 聊天顺手记录好消息 → 14/30 天用真实历史生成报告。
P1：形成持续陪伴｜日终记忆整理、主动消息策略、点子场景库、用户可见记忆管理、14 天回顾、常见学堂内容检索。
【你提出的场景】用户在“重新认识我”选了三天没健身时的陪伴方式，后续 Web 站内提醒遵守该偏好；重要的“喜欢寿司”记忆不会因日终整理丢失。
P2：提高惊喜与深度｜30 天精致报告、丰富进化分支、更多学堂内容、艺术素材更新、进阶的检索与报告模板；移动 App 与生物 AI 生成后置评估。
【你提出的场景】宠物进化沿既定素材分支成长，30 天生成精致模板报告；若以后再开放 AI 生成幻想形象，应单独评估模型、成本与一致性，不影响首版可交付性。
并行协作接口｜创意确定场景与规则；技术定义工具协议、数据模型与接口；UI 给出聊天/计划/报告的状态设计；三方共用同一套验收脚本。
【跨团队落地拆解】“喜欢寿司”明确记忆、“三天没健身”事件、“120 XP/四类各 30 XP”规则同时映射到创意需求、数据库字段、Web 提示状态和测试用例，避免三组人各说各话。
近期交付与风险控制｜把当下目标设为“可信的第一条用户旅程”；每周演示场景成品，先解决速度、工具正确性和资料隔离，再推进复杂成长系统。
【你提出的贯穿体验】现场演示同一个小光如何记住喜好、理解未完成健身不是人格失败、说明成长规则，并在网页版展示宠物成长及蜕变报告的入口。

03  UI 方向｜用户体验
UI 首要原则｜先把桌面网页版做成 Agent 为中心的可信工作台，布局参考 Muse 的“Agent 主视图 + 其他功能入口”；移动端不是首轮设计优先级，而是 Web 产品稳定后基于同一信息架构迁移。小光 Agent 与成长宠物在视觉和状态系统上分离。
3.1 页面设计
网页版首页｜设计桌面宽屏版的 Agent 主区域：稳定的小光视觉形象、聊天记录及输入区居于视觉中心；侧边栏/辅助区域放计划、好消息、成长、我的空间等入口；点子和心灵学堂应易发现但不抢主聊天注意力。
【你提出的参考】以 Muse 的 Agent-first 页面组织为参考，而不是照搬其全套功能；用户进入 Web 首页先能自然和小光说话，同时清楚看到侧边栏的成长、计划、点子与心灵学堂。
聊天作为网页版主工作台｜对话和功能执行不割裂：小光可以调取计划、记录好消息、解释积分和宠物进化规则；关键结果在聊天里有清晰反馈，并能跳转对应 Web 页面。
【你提出的场景】用户问“小光，下一次进化要达到什么条件？”小光查询规则作答；点击“去看成长”可打开独立宠物成长页，聊天里的 Agent 形象无需变化。
首登引导｜约 10 分钟场景问答可选择在初期完成，允许跳过；以生活化二选一/简答为主，避免开场一次性收集过多敏感信息。
【你提出的场景】点子“重新认识我”做大约 10 分钟的情境式问答，例如“三天没健身，你希望我怎么办？”用于建立可编辑的互动偏好，而不是把问卷变成死板的人格测评。
状态统一｜聊天页、计划页、好消息页和成长页读同一后端状态；加载、空数据、执行失败、部分完成必须有清晰设计。
【基于你的 XP 案例补充】用户在 Web 聊天里完成行动后，侧栏成长值和宠物页显示同一后端计算出的 XP；计分遵守来源上限，不以动画演出替代真实落库。
Web 优先、移动后迁｜首轮以 PC/桌面浏览器的导航、窗口布局、鼠标/键盘交互为主要设计与验收对象；同时保持响应式基础，便于网页在窄屏能使用。移动 App 等 Web 主流程成熟后基于它迁移和适配，而非倒过来决定桌面布局。
【你提出的落地场景】第一版只部署服务器 Web：用户收到的是聊天窗口里的主动消息；打开网页后查看，不能宣称手机锁屏会弹通知。后续做 App 时，再研究导航折叠、移动输入和系统推送。
3.2 美术风格
美术气质｜优先围绕“小光 Agent 的亲和、简洁、稳定”建立视觉系统，可参考 Muse 的排版气质和 Grok Bot 的交互形象表达；成长宠物作为独立的奇幻养成世界，风格相关但不要求与 Agent 同形态。
【你提出的参考】聊天主角可以像 Grok Bot 那样保持相对稳定、具有轻微生命感的视觉呈现；用户真正看见的“升级变化”优先发生在个人宠物成长页，而非每次修改小光本体。
两个视觉层｜①小光 Agent：简洁、识别度高、相对稳定，适合长期放在聊天主视图；②个人成长宠物：可探索细胞、蝌蚪、乌龟至山海经风格幻想生物。两套素材可在色彩和品牌气质上统一，但资产与进化逻辑分开。
【你提出的场景】用户在 Web 聊天主页看到固定的小光交互形象，到“成长进化”页则看到自己的宠物正走在一条进化路径上；报告卡继续用设计师制作的高质模板。
网页版的使用性能｜首版优先关注桌面浏览器加载速度、聊天滚动、大量历史消息、不同窗口宽度和低配置 PC 的表现；动画可降级。移动端专项优化放到迁移阶段，而不是以省电手机场景指导第一版。
【Web 验收补充】在常见笔记本分辨率、半屏浏览器以及宽屏桌面上，确保侧栏、聊天框、宠物页卡片不重叠，输入和阅读体验稳定。
素材授权｜现有演示球体或参考站视觉仅用作方向讨论。上正式产品之前核实商业授权，优先采用原创可控的素材体系。
【你提出的参考】从 Muse 借鉴 Agent 主导的布局，从 Grok Bot 借鉴形象表达，不直接复制其品牌素材、受限动效或代码。
待确认  先共同确认一页视觉 Moodboard：温暖程度、神秘程度、卡片质感、动效频率、拟人化强度，避免三个设计师做出三个产品。
3.3 Agent 形象
小光 Agent 的形象与个人宠物必须明确分开｜“小光”是同一个 AI 伙伴及聊天中的交互主体；“个人宠物”是用户成长游戏系统中的独立养成对象。二者可有关联互动，但不能被视为同一角色必须同步变形。
【你刚刚明确的原则】聊天中的小光初版可以直接采用 Grok Bot 那类相对固定的视觉呈现；成长值变化、形态解锁发生在用户的个人宠物路线里，不要求 Agent 头像因此重绘。
Agent 首版形象｜采用一套稳定、轻量、可复用的形象资源（如简洁的动态角色/光球表达），仅设计少量倾听、思考、回应等状态。无需对接生图模型，更不要求每一成长阶段都调用生图改变 Agent 本体。
【你刚刚提出的取舍】如果为了让小光本体跟着每个进化等级改形态，需要生图模型和一致性治理，就先不做。第一版重点先把 Grok Bot 式稳定形象、对话反馈和工具调用体验做顺。
个人宠物成长路径｜在独立的成长页呈现经验值、徽章、解锁节点和宠物形态。路线可从细胞、蝌蚪、乌龟发展到山海经灵感的奇幻生物；初期采用人工制作或审核通过的有限素材库。
【你提出的场景】用户累计真实经验值后，宠物从初始形态解锁下一阶段；用户仍然在同一个小光聊天窗口问“还差多少 XP？下一阶是什么？”小光从系统读取正确答案。
宠物分支可解释、可回看｜宠物外观变化只由成长系统控制，显示规则、等级和历史图鉴；不把“用户一天没做任务”演出成宠物受惩罚，也不自动变更小光的聊天人格。
【你提出的 XP 场景】每日 XP 暂按 120 总上限、来源各 30 作讨论示例。用户可以在成长页查看数值、解锁条件和宠物已走过的分支，无法通过反复发送同一条聊天无限涨级。
生图模型不属于初版依赖｜后续如考虑 AI 生成的专属宠物或自定义神兽，再单独评估：角色一致性、连续多阶段画风、版权、延迟、审核与调用费用；不能让这些阻塞第一版。
【后期选项，不是初版需求】将来可以探索个性化幻想宠物的有限定制，但首版只用预设演化资产就能交付完整的成长体验。
3.4 功能分区
桌面 Web 功能分区｜以小光 Agent 聊天区为主，桌面侧栏放清晰的页面入口。八个产品模块必须能找到，但不等于八个同权重标签；优先按聊天高频任务、成长查询和内容探索划分层级。
【你提出的参考】学习 Muse：聊天占视觉主体，其他功能放侧栏或次级入口。用户点击“点子”探索玩法，点击“心灵学堂”查团队审核的内容，再随时回到同一个 Agent。
先定义 Web 导航，再做移动端迁移｜桌面导航建议为可收起侧边栏+主聊天面板，必要时附上下文卡片区域。等网页版验证后，再把同一模块关系转换成移动端底部导航或抽屉导航；当前不以“底部四 Tab”作为主设计假设。
【你提出的开发顺序】先让网页版小光 Agent、蜕变计划、成长宠物、我的空间、点子和心灵学堂的入口可用且结构清晰；后续手机端根据网页的信息架构迁移，而不是让 Web 模仿一个尚未实现的 App。
我的空间内容结构｜个人档案、记忆纠错、好消息时间线、隐私与通知设置、报告入口按用途分层；不要把“重新认识我”封死在设置里。
【你提出的场景】“重新认识我”应作为点子库里的独立体验入口；完成提问后，用户可以到“我的空间”查看和更正刚刚确认的偏好，不另造冗余设置模块。
点子与学堂必须区分｜点子是“点击后让 Agent 带我体验”；学堂是“阅读受审核的知识并进入练习”。两者卡片样式和行动文案应有清晰差别。
【你提出的场景】点子中的“现在小光有多了解我”是可直接玩的交互场景；学堂中的“水桶效应”则是团队审核知识文章，小光可解释和引导阅读，两者功能不能混淆。
报告的专属展示｜报告不是一条极长的纯文本聊天消息，而应有封面、故事节点、可核查的记录及隐私可控的分享预览。
【你提出的场景】14/30 天后的蜕变报告使用设计师制作的精致卡片模板，AI 提炼真实故事并填内容；普通分享卡可采用更灵活的模板，但外发前都需用户预览。
